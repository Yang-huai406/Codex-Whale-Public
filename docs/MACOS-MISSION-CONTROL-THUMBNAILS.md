# 2026-10-10 macOS Mission Control 顶部桌面缩略图真实对照

**已完成本机兼容修复，并由用户验收正式启动的版本。** 本文记录定位过程、实现和验证范围；不声称已查明 WindowServer 私有合成算法。

范围仅限：Mission Control 顶部 **桌面缩略图（Space 预览）** 中，原生 Codex 窗口与桌宠透明覆盖窗口是否能同时显示。

## 2. 实验记录（观察）

“观察”= 用户实际看到的画面，或从进程读回的值；“推断”单列于第 3 节，不与观察混记。

| 轮次 | 变更 | 观察结果 | 可用性 |
| --- | --- | --- | --- |
| A 基线 | 桌宠为原尺寸 1205x890，正常周期重排 | 顶部缩略图中 Codex 消失，只剩桌宠 | 复现稳定 |
| B 基线补充 | 暂时通过 IPC 退出桌宠 | Codex 恢复完整 | 说明消失与桌宠窗口存在相关 |
| C | 保留原宽度，仅去掉/停掉 16ms `moveAbove` | Codex 仍然消失 | 排除“仅周期性窗口重排”这一单因 |
| D | 宽度减 1 点至 1204x890 | 第一次报告为正常 | **不可单独作为通过依据**，见下 |
| D′ | 同上，用户再次打开 | 用户报告桌宠消失；该轮存在停止重排/遮挡混淆 | 该轮状态不干净，作废重测 |
| E | 恢复原宽度 1205x890 | 用户又报告 Codex 消失，只剩桌宠 | 与 A 一致 |
| F | 恢复正常周期重排，且在同一桌宠进程内仅减 1 点宽度（1204x890） | 用户连续两次进入展开顶部预览并退出，均确认 Codex 与桌宠同时显示 | 本轮唯一可重复的正向观察 |
| G | 恢复原宽度 1205x890，周期重排保持开启，层级仅改为 3（floating） | 用户确认仍只有桌宠，Codex 消失 | 与 A 一致 |

关于 A 的初始描述：当时用户描述为“Codex 消失，只显示异常放大的桌宠”；本轮基线用户确认为“Codex 消失，只有正常大小桌宠”，即**本轮没有重现桌宠异常放大**，因此本文不宣称已证明异常放大与消失的因果关系，也不对异常放大的原因作任何结论，只记录“原尺寸 1205x890 下同样出现消失”。

轮次 D 的第一次“正常”与轮次 D′ 的用户报告相互矛盾，且 D′ 期间还有停止重排与遮挡干扰，因此 D 系列整体不作为通过依据。

## 3. 区分：观察 vs 推断

**已实测（观察）**

- 在 1205x890、与宿主同边界、`opaque=false` / `backgroundAlpha=0` 的透明覆盖下，顶部缩略图中 Codex 消失、仅剩桌宠，重复出现。
- 退出桌宠进程后 Codex 恢复完整。
- 仅停止 16ms `moveAbove` 不足以改变结果。
- 在同一桌宠进程内把宽度减 1 点至 1204x890，并保持正常周期重排时，用户连续两次展开/退出顶部预览都看到两者同时显示。
- 把 level 停在 0 或 3（floating），结果相同。

**推断（未验证）**

- 触发条件与“透明覆盖窗口与宿主窗口同边界”相关；**最小实际窗口宽度差异可规避**这一现象。这是对实测结果的归纳，不是对系统内部机制的解释。
- WindowServer 可能按窗口几何（边界/覆盖关系）处理覆盖判定与缩略图可见性。这属于推断：**未验证系统私有内部算法**，本文不给出机制性结论。
- `kCGWindowAlpha=1` 只表示该窗口字典字段取值为 1，**不能说成“窗口背景不透明”**；本窗口 `opaque=false`、`backgroundAlpha=0`，两者不矛盾，含义不同。
- 周期重排与 level 0/3 在**本轮**都不是直接因素：停止重排（C）和切换层级（G）都未改变结果。这仅限本轮样本，不外推到其他配置。

## 4. 检测手段的边界

- `SLSManagedDisplayIsAnimating` 在已采集到的调度中心变换样本中存在返回 `false` 的情况，因此**不能仅靠该检测判断当前是否处于调度中心**。
- 本轮判定以用户对顶部缩略图的目视确认为准；系统接口读回值只作为辅助，不能替代目视确认。
- 中央 Exposé 窗口分别排列与顶部桌面缩略图显示是**两种不同的验收对象**。本文只交付顶部预览兼容规避，中央窗口共同排列仍未解决。两者结论不可互相引用为已解决。

## 6. 已实现的兼容修复

`desktop/macos/follow.cjs` 的 `companionBounds` 从宿主的模型坐标计算桌宠矩形，**在右边界留出最小 1 逻辑点差异**（即取整后的宿主宽度减 1），避免与宿主窗口边界完全重合。`desktop/main.cjs` 首次创建跟随窗口也使用同一规则。反复 tick、窗口移动/调整大小和重新绑定都从宿主矩形重新计算，不能从桌宠旧尺寸连续减小。

诊断状态分别提供 `hostBounds` 与 `overlayBounds`；宿主元数据继续保留完整尺寸。该规则仅用于 macOS 跟随模式；Windows 和独立桌面模式不使用这个边界差异。代价是透明承载窗口最右侧减少 1 逻辑点，右侧布局可用宽度相应减少 1 点；没有缩放桌宠画面。

| 约束 | 说明 |
| --- | --- |
| 性质 | 属于**系统兼容规避**，不是对 WindowServer 内部行为的修复 |
| 透明度 | 不变（仍 `opaque=false`、`backgroundAlpha=0`） |
| CSS 缩放 | 不变 |
| 窗口裁剪区域 | 不变 |

## 7. 跟随窗口层级与遮挡

本次另一项改动仅影响跟随模式的窗口层级：取消 `floating` 置顶，与 Codex 一样使用普通层级。有效的原生绑定样本应用后，若宿主和桌宠均可见，调用 `moveAbove` 维持桌宠在已核实的 Codex 窗口上方；覆盖 Codex 的其他普通窗口仍可覆盖桌宠。

- 不在 Space 动画期间重新排序、移动或显示。
- 用户隐藏、宿主隐藏、绑定失败或心跳过期时，不通过排序强行显示。
- 排序失败进入已有失败隐藏路径，后续有效样本可恢复。
- 切换到独立桌面模式仍使用 `floating`；返回跟随模式取消置顶。
- 此调整改善普通桌面的遮挡关系，不是顶部预览修复的根因证明，也不建立中央概览所需的父子窗口关系。
